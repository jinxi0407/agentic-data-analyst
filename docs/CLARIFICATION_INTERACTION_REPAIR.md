## A：有效城市补充失败的根因

第一次真实 API 复现保留于忽略目录 `logs/clarification/initial_reproduction.json`。
第一轮 request_id `80c61fd8-24b3-452b-b797-c20791d8e78a`：正确询问具体城市，未执行 SQL。
第二轮 `49d77168-6ea7-48d5-aa30-ff9d63badfc9`：UI/API 使用同一原问题、待补 entity、原反问和轮次1，回答“南京市”。

捕获到两个不同的错误，不能笼统归因于城市不存在：

1. 模型输出 `proceed`，却保留原非空反问，`Decision.consistent` 拒绝，错误位置为根节点，类型 `value_error`，原因 `Proceed must be complete`。
2. 既有一次格式重试清掉反问，但又将“南京市”同时放入 `known_constraints` 和 `resolved_slots`。
   “南京市”不在原问题中，`validate_evidence` 以 `Known constraint is not grounded in original question` 拒绝。

MySQL 实际存在 `users.city='南京市'`。错误不是 UI 没传回答，不是数据库连接失败，也不是 city 缺失判断需要删掉。
原先第二轮要求模型重复输出原条件、反问、已补字段等冗余信息，造成字段来源混淆；重试提示未能消除这种结构负担。

### 修复

`app/agent/scoped_clarification.py` 新增独立 `FollowupDecision`，只允许：

```json
{"decision":"proceed","resolved_slots":[{"slot":"entity","quote":"南京市"}],"missing_slots":[]}
```

这是结构示例，不是南京市专用逻辑。所有被问字段共用同一验证路径。
原问题和原条件由服务端 context 保存，模型不再重述 `known_constraints` 或原反问。
补充引用仍必须是实际回答中的原文，字段必须曾被询问，全部被问字段必须补齐才能执行。
`needs_rephrase` 仍要求明确缺失字段；禁止第二次反问、未问字段注入和伪造引用。
保留一次格式重试及 JSON Object 传输，未恢复 strict JSON Schema，未增加新的 Repair Loop。

## B：表现最好未追问

首轮 request_id `141053be-c91b-45e8-8f76-008251f5f4ed` 捕获的原始决策本身就是合法 `proceed`。
这次不是 validator 将不完整 clarify 改为 proceed。SQL 随后自行按 `SUM(order_items.item_amount)` 排名。
现有生产 `BUSINESS_CONTEXT`、`STATIC_SCHEMA_METADATA` 和别名映射没有“表现最好默认销售额”的唯一契约。
销售额的计算定义不能代替排名指标的选择。因此这是 Gate 漏判指标歧义，不是已明确的默认解释。

初轮提示增加通用约束：比较性描述本身不选定 KPI；需由问题或契约明确指标。
没有匹配某句或某个中文关键词的 if/else。
同时修复真实存在的安全问题：旧 `InitialDecision` 在 clarify 证据不全时会强制改为 proceed。
现在它报结构错误，经过原有最多一次格式重试仍失败则停止，不默默关闭 Gate。
24会话中，R04两次都先问指标；R05/R06/R07明确指标的对照均直接执行。

## 客户 Top5 的独立 SQL 问题

使用固定问题“以2026年9月12日为今天，最近30天消费金额最高的5个客户是谁？返回用户ID、姓名和消费金额。”审核：

- 显式参考日期进入引擎，SQL 使用2026-09-12而不是系统当天。
- 下界 DATE_SUB(2026-09-12, 30 DAY) 为2026-08-13。
- 使用 SUM(orders.paid_amount)、有效订单状态、users→orders 正确 FK、用户粒度分组、金额降序及 LIMIT 5。
- 没有订单明细/退款一对多 JOIN，因此这条 SQL 没有 JOIN 扩增金额问题。
- SQL 额外加入 `order_date <= '2026-09-12'`。既有契约及其示例只定义 DATE_SUB 下界，没有这个上界。
- 数据库在参考日后有1187张订单（2026-11-01至2026-12-28），因此额外上界实际改变结果，不只是写法不同。

增加截至参考日的上界在自然语言上有合理性，但与当前已有的仅下界契约不一致。
本轮保留该争议并按既有契约标记不匹配，不修改引擎、契约、历史标准答案或数据库来消除差异。

## 诊断与 UI

- UI 创建 request_id，API 回传同一 ID；补充请求使用新 request_id，并通过 parent_request_id 关联第一轮。
- 日志覆盖 UI 提交、API 模式、Gate 原始结构化字段、Pydantic loc/type、字段证据、合并输入、SQL/执行状态。
- 只保存定位所需字段，不记录隐藏推理、完整环境变量或密钥。日志仅在 Git 忽略目录 `logs/clarification/`。
- 格式校验失败返回 `gate_validation_failed` 和结构化错误位置；运输异常、实体未解决、信息不足与 SQL 失败分开记录。
- UI 保留失败补充与 pending context，新问题或模式切换清除旧状态，示例按钮更新实际提交内容。
- 请求期间禁用交互提交，单次请求只处理一次；响应 ID 不匹配不显示结果。
- 显示实际模式、简短 Gate 决策、request_id 及补充字段，不展示隐藏推理。
- “成功”改为“查询已执行”，明确执行成功不是人工核实语义正确。
- API 缺省 direct 未变；OFF 不调用 Gate 的测试保留。
